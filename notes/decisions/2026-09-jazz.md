# Storage: Jazz v2, on trial (Sept 2026)

**Decision.** Quizzes and workspaces move from libSQL (Turso's SQLite, in local-file mode) under
Drizzle to **Jazz v2** (`jazz-tools`, pinned to a 2.0.0 alpha). Jazz is a local-first relational
database: each browser keeps its own copy (IndexedDB), writes land there first, and a sync
server carries them to other devices and other people. Nothing of the old database survives:
not the schema, not the migrations, not Drizzle, `drizzle-zod` or `drizzle-kit`. There is no
migration path; the Coach's quizzes come back through the import tool.

**Turso is out, now and for later.** Two concerns decided it: concurrent access from several
tabs, and a conflict resolution that is last-push-wins in some cases.

**This is a deliberate exception** to the stack's four-way test. Jazz v2 is in alpha, and it is
newer than the agent's training cutoff. We are taking it anyway to put the app in front of
possible users and learn what they need before we commit to infrastructure. It settles the
question `stack.md` had left open, *what the product is, and so where the database lives*: a
local-first app, with the database in the browser and a sync server behind it. The hosting side
of that is `2026-09-client-first.md`.

**The trial is about requirements, not about Jazz.** If we later leave Jazz, what we learned
about requirements carries forward to the next choice. The Jazz code will not.

## The shape of the data

* **Rows, as if we had been Jazz from the start.** The editing actions write rows; the views
  subscribe to rows. The reducer-over-a-tree design goes. A quiz "document" (the bag a formula
  reads, the export, the git mirror's file) is a projection assembled from rows, never a store.
* **The relational shape lives in `schema.ts`, in Jazz's DSL; every structured value lives in
  Zod.** Tables and their scalar columns are *not* authored in Zod: `JZS.string()`, `JZS.int()`,
  `JZS.enum()`, `JZS.rel()` and so on, carrying no constraint beyond their type (no length, no
  pattern). Only a column holding a structured value takes Zod: `JZS.json()` accepts a Zod 4
  schema directly (through `~standard.jsonSchema`), converts it to JSON Schema draft-07 for the
  column, and infers the row type from it. The conversion is lossy (transforms, refinements,
  coercion and function defaults do not survive), which is fine: the same Zod schema runs in
  full at the entrypoint before the value reaches the column, and the column's copy is a second,
  weaker net. Row types come from `JZS.RowOf<>` / `JZS.InsertOf<>`. One exception, while
  alpha.56 lasts: a JSON column made optional refuses every value, so a structured value that
  may be absent is stored as JSON text (`jsonText<TT>()` in `src/db/json-text.ts`), and only
  its row validator checks it.
* **Every scalar field still gets its Zod check, so each table is declared twice.** The Jazz
  table (shape, relations, merge) and a Zod row validator in `models/` (`label` with its regex,
  `titleish.max(82)`, `uint`), applied at every entrypoint and before every insert or update.
  Document validators (a quiz with its questions, for import and export) are compositions of
  the row validators, never a third copy. Deriving one from the other was weighed and refused:
  a mapper would cost Jazz's per-column query typing and need a side channel for what Zod
  cannot say. Instead, **one generic coherence test** (`tests/db/coherence.test.ts`) walks
  every table and asserts: same columns, same nullability, same base type, same enum values,
  byte-equal JSON schemas on `JZS.json()` columns, relation columns are id fields (`rowid`), and
  the Zod output type equals `JZS.RowOf<>` minus `id`. A constraint that lives only in Zod is
  invisible to it by design.
* **Column-level nuance is Jazz's, declared on the column, and not in the first pass.** Merge
  strategies (`lww` default, `counter`, `g-set`) and text diffs (`Db.update`'s `applyDiffs`) are
  DSL-side; Zod never sees them. Every text starts as `JZS.string()`, last-writer-wins.
* **Ids are internal details.** Jazz owns `id` (a UUID; no table may declare its own) and we
  never show one. Where a label relationship is reasonable and equally powerful, use the label,
  scoped where it must be: `quizlabel-questionlabel` as a selector id, labels in formulas, URLs,
  exports and git paths. ULIDs and `lib/ids.ts` go with the rows.
* **Field names stay `underscore_case`.** Jazz reserves only `$`-prefixed names and `id`, and its
  own docs use `owner_id`, so nothing forces a change. If Jazz ever turns out to be opinionated
  about camelCase somewhere, transition that spot wholesale; no mixed names.
* **Provenance is Jazz's.** `$createdAt`, `$createdBy`, `$updatedAt`, `$updatedBy` replace our
  `created_at` columns. "The newest playing for a player and text" is an order by `$createdAt`.
* **Composite keys go.** `(quiz_id, label)` becomes a row with `JZS.rel()`; label-uniqueness within
  a quiz is enforced by the app, as it already is.
* **Payload-bearing enums** (`JZS.enum({ expression: {...}, player: {...} })`) would give
  `widgets` a real tagged union rather than columns that are null for the other kind. alpha.56
  refuses every insert into one, so `widgets` keeps a nullable column per kind for now, and its
  row validator says which kind holds which; a canary test says when that changes.
* **Merge is per column, last-writer-wins** (plus `counter` and `g-set` for arrays). Two people
  typing the same clueing at once: last wins, no character-level merge. Acceptable for the trial;
  a Google-Docs feel for some text fields is a recorded TODO, not an expectation.

## Validation

Validate **between the UI and the app** (a field's new value being submitted, an import, an ask
reply) and wherever else it is natural, with the same Zod schemas the columns use. We do not rely
on the database alone: a write refused by the runtime makes a lousy message and is hard for a
front-end developer to see or triage. Add every check the tools make easy: Zod on JSON columns,
`JZS.enum()` where a column is a closed set, `.optional()` only where null means something.
Length limits (`titleish`, `noteish`) cannot sit on an `JZS.string()` column, so they are entrypoint
checks, as `guidelines.md` already has them.

The runtime does enforce a `JZS.json()` column's schema (verified on alpha.56): an insert that
breaks it throws synchronously, before any sync, naming the column and the first problem. It
checks only what JSON Schema can say, so it is a second net, never the message an author sees.
Hand the column `plain(...)` of a `Validator` callable: the callable compiles, but drops its own
top-level `.describe()`, since Zod keys that metadata on the schema's identity.

## Rules that follow from it

* **Work from the installed source, never from memory.** The `jazz` skill says where to start: the
  installed `jazz-tools` version, `schema.ts`, `permissions.ts`, the provider setup. Where the
  installed source and the public docs disagree, follow the source and say so.
* **Authorization lives in `permissions.ts`.** Hiding something in the UI is not a permission.
  Client-side `db.canRead()` and friends are advice; the sync server is the verdict.
* **Writes are local-first.** Wait for a sync receipt (a durability tier) only when the
  operation needs one, and in tests, wait for the tier the assertion depends on.
* **Read flat.** In alpha.56 a query that includes several relations, or nests one include in
  another, can hang the page. One query, or one subscription, per table; assemble the tree with
  `quizFrom`.
* **Write through `perform`, one transaction per action.** Each action validates every row it
  touches, writes only what changed, and lands whole or not at all (`transact`). It acts on the
  quiz the screen shows, never on the synced `active_quiz_id`.
* **Don't cache live queries.** A Jazz subscription is already the store; don't wrap it in
  another one.
* **The quiz's git repository is still not a source of truth.** Moving to Jazz changes where the
  quiz is stored, not what the git repo is for: past versions to compare, and an exit door.
* **Pin the version.** An alpha changes under you. Bump it on purpose, not by accident of the
  lockfile.
* **Import the schema builder as `JZS`**, never `s`: `import { schema as JZS } from 'jazz-tools'`,
  then `JZS.table(...)`, `JZS.string()`, and the types `JZS.RowOf<typeof app.quizzes>`. Jazz's
  examples use `s`; a one-letter name is against `STYLE.md`, and `JZS` reads as what it is.
* **Jazz's admin and backend secrets come from Doppler**, like every other secret, and live
  only in the *janitor* configs (`dev_janitor`, `dev_aijanitor`, `prd_janitor`). The app never
  needs them: a browser needs only `NEXT_PUBLIC_JAZZ_APP_ID` and `NEXT_PUBLIC_JAZZ_SERVER_URL`,
  and a production build bakes those in, so they must be present at build time.
* **Publishing the schema to a real database is housekeeping, not a side effect of running.**
  `JAZZ_REAL_DB=true` marks a config that names a real database; in dev, anything else gets a
  local Jazz server that republishes on every save. `scripts/jazz_deploy`, under a janitor
  config, publishes schema, permissions and any needed migration, and goes before a release
  that changes them. `scripts/jazz_healthcheck` says, without changing anything, whether a
  database answers and holds our schema.

## Identity: local-first now, a hub later

A Jazz local-first account is a real, authenticated account: a random signing root in browser
storage, verified by the server, no login. That is the app's starting state, and for the trial
it is the whole story: an author opens the app and works. (`--allow-local-first-auth` must be on
in production.)

The path to "identified" is agreed and deferred (TODO 1 below):

* **One issuer, federating Google.** The Jazz server trusts one JWKS URL, so "Google now, others
  later" means a hosted hub (Clerk or WorkOS: no backend of ours) with Google enabled first.
  Raw Google Identity Services would leave token refresh to us and could never share the server
  with a second provider.
* **`linkJWT` at the threshold.** Signing in attaches the identity to the *existing* account; id
  and rows are preserved. No copy, no weirdness.
* **The one seam is a collision**: the identity already belongs to another account (signed in on
  the phone before linking on the laptop). Jazz never reassigns an identity. Policy: copy the
  local account's quizzes into the identified one, then switch. Written down so it is designed,
  not discovered.
* **Better Auth is the named alternative**, not the choice. Its Jazz adapter stores Better Auth's
  own tables (user, session, account, verification, *jwks*) in our Jazz database, but Better Auth
  itself is a route handler on our server, in the path of every login and refresh. Reasons to
  pick it later anyway: owning the user table, no per-user pricing, one fewer third party.
* An account can carry several identities, so changing providers later is link-then-retire,
  not a data rewrite. The door swings.

## What it replaces

`src/db/` (the Drizzle schema, the connection, the repositories), `/drizzle`'s migrations, the
workspace and players route handlers and their `port.ts` files, the cookie that told a browser
which workspace was its own, `state/workspace-store.ts`, the reducers as functions over a tree,
`lib/ids.ts`, and `tests/db/`. The players table becomes a constant; the ask route stays.
