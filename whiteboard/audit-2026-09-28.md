# Audit, 2026-09-28

A general audit of the codebase after the move to Convex, asked for by the Coach. Five
questions: style and framework mismatches; the query boundary; database residue in the models;
hand-rolled or workaround code; and what is more complicated than its purpose. Read the whole of
`src/`, `convex/` and the notes; `pnpm lint` and `pnpm typecheck` were both clean at `2c579f6`.

The short version: the domain code (models, `convex/`, the grid) is in good shape and mostly
follows STYLE.md. The residue is in three places: a personal utility library under `src/lib/`
that the toolkit already covers and nothing uses; the tree-shaped side of the models, which
still assumes the browser builds whole quizzes; and a handful of local-first habits in the views
that were free under Jazz and now cost a round trip. The query boundary is defensible as built,
and the "never a query per row" line should be replaced rather than restored.

## 1. Style and framework mismatches

Mechanically enforced style passes; these are the things the linter cannot see.

**Iteration names outside a `for` loop.** STYLE.md reserves `ii`/`jj`/`kk` for a literal loop's
own variable and forbids them as lambda parameters. Violations:

* `src/models/hunt.ts:58-74`: `(ii) =>`, `(rr) =>`, `(qq) =>`, `(realm, rr) =>`, `(quiz, qq) =>`,
  `(widget, ii) =>`. Should be `idx`, `realmIdx`, `quizIdx`.
* `src/lib/importing.ts:128`: `(question, jj) =>`.
* `qq` as the index-range builder in every `withIndex((qq) => qq.eq(...))` under `convex/`.
  Convex's own idiom is `q`, which the no-single-letter rule forbids, and `qq` is the
  compromise the phase 1 agent reached for. It is used consistently and reads fine, but it is
  not in STYLE.md's list. Either record it beside `CVX` (recommended: it is the same kind of
  "framework says one letter, we say two" decision) or rename to `range`.

**Development notes in doc blocks.** guidelines.md says progress notes and future work go in
`HUMAN-whatsup.md` or `/whiteboard`, never in a doc block. Found in:

* `src/models/review.ts:32` and `src/components/panels/ReviewsPanel.tsx:11`: "PR 6 moves this
  rule into the server's policy".
* `src/lib/collections.ts:186`, `src/lib/vv/checks/numbers.ts:13`, `src/lib/vv/reporting.ts:234`,
  `src/lib/strings.ts:230`: "the relic spelled this", "as the relic had it", "under its older
  name". These describe where the code came from, not what it does for a caller.

**Naming drift.** Local variables for ids are `quiz_id`/`question_id` almost everywhere (matching
the field), but `quizId` in `src/state/commit-scheduler.ts:26-87` and `quizId`/`questionId` in
`src/components/ExpressionFields.tsx:45-46`. Index locals are `onto_idx` (an action field, so
underbar is right) but then `from_idx`, `over_idx`, `seatIdx`, `open_idx`, `locked_idx` are
mixed. STYLE.md wants `fooIdx` for a local. Pick one and sweep; the underbar rename commit
(`7f2a1ee`) also left `bot_label:` misaligned against its neighbours in `models/botting.ts` and
`models/widget.ts`, which is the kind of column alignment STYLE.md asks for by hand.

**`fill` signatures.** Every model's `fill` takes a DNA bag except `Ident.fill(label, title)`
(`src/models/ident.ts:54`), which takes positionals and returns the row type rather than an
`IdentT`. Make it `Ident.fill({ label, title })`.

**Quote convention.** STYLE.md says `'` by default and `"` only for a key that must be quoted.
The notices use `"` for any string with an apostrophe (`src/lib/notices.ts`, 14 lines), while
the models escape apostrophes inside `'...'` (about 50 `\'` across `src/models/`). Both are
defensible; STYLE.md should say which, and I would say the notices have it right (an escaped
apostrophe in prose is harder to read than a double quote).

**Framework practice.**

* `src/components/QuizHeader.tsx:29-34` dispatches `retitle_quiz` on every keystroke as well as
  on blur ("the one field that updates live"). Under Jazz that was a local write; under Convex it
  is a mutation per keystroke, each of which reruns `hunts.open` for every open browser of the
  hunt. This is the clearest piece of path dependence in the views. Blur-only, like every other
  field, is the fix; `useDraft` already does it.
* `useHunt` and `useQuiz` set state during render (`use-hunt.ts:214`, `use-quiz.ts:43`). React
  sanctions the pattern ("storing information from previous renders") but it is the subtle form
  of it, and both hooks reach for it. A `useMemo`-with-ref or a reducer would read more plainly.
  Not wrong; worth knowing it is there.
* Three idioms for "not loaded yet": `useHuntsList` returns `null`, `useQuiz` returns
  `undefined`, `useIdent` returns a `{ loaded }` flag, `useHunt` returns a `finding` word. One
  convention would do. The `Finding` word is the most honest of them (it distinguishes waiting
  from missing) and could be the one.
* `React.JSX.Element`, `React.ReactNode`, `React.KeyboardEvent` are used as a global namespace in
  several components without importing `React`. It compiles under the automatic runtime's types,
  but it is the one place the code relies on an ambient global; `import type { ReactNode }` is
  the ecosystem's grain and what `app/layout.tsx` already does.
* `reviews.forQuiz` (`convex/reviews.ts`) hands every review, drafts included, to every browser,
  and the smith's panel filters to shared ones on the client. Known and marked for the
  permissions phase; noting it here so it is on the list rather than only in a doc block.

**Vocabulary left over from Jazz.** `SyncProvider`, `SyncNotices.tsx`, `SyncUnconfigured` and the
`(synced)` route group all say "sync", which was Jazz's word for its server. Convex's word is the
deployment or the database. Cheap to rename; the vocabulary note never defined "sync".

## 2. The query boundary

### 2a. What should govern it

The "never a query per row" line was written for Jazz-era instincts and for a worry about
subscriptions per component. It is too strident because it names the wrong thing: the cost in
Convex is not the number of queries, it is the read set and the result size of each one. A rule
that fits what Convex actually does:

**A query per thing that changes on its own. A hook per thing a screen shows. A component never
subscribes.**

Spelled out:

1. **Draw the boundary by churn and size, not by the component tree.** Convex reruns a query
   whenever anything in its read set changes, and sends the whole result whenever the result
   differs. So the unit is "the set of rows that change together, projected to what the screen
   shows". Split a query when a large result has a small part that changes often (a quiz's
   questions: one author edits one). Merge when the parts always change together or are always
   shown together (the frame: quiz fields, widgets, columns). This is exactly the frame plus
   per-question split now built, and the measurements bear it out (46 KiB to 3 KiB per edit).
2. **The server assembles; the client only stitches siblings.** A query returns a screen shape
   projected from rows (`lib/rows.ts`), never rows the browser has to join. The browser may
   assemble sibling subscriptions whose union is a screen (`assembledQuiz`), but never look up
   across tables itself.
3. **One hook owns a screen's subscriptions; components take props.** `useHunt` and `useQuiz`
   are the pattern. No `useQuery` inside a cell, a row or a dialog. This is the half of "never a
   query per row" that was right: a subscription per *component* is what makes a grid
   unpredictable, and `useQueries` in one hook is how a dynamic set of subscriptions stays a
   single, batched thing on one socket.
4. **"Per row" is fine when** the row is the natural unit of change, the count is bounded (the
   999 cap), and the ids are known from a parent subscription. It is wrong when the set is
   unbounded (paginate) or when the screen wants a computation across rows that belongs on the
   server (a sort reads every question, and does so in the mutation).
5. **One-shot reads for on-demand, large, non-live things.** `client.query` for the export; never
   a subscription to the whole hunt.
6. **Measure in database I/O per edit and bytes per browser per edit.** The phase 4 harness
   exists; a boundary change without a before-and-after number is a guess.

Two boundaries that do not yet follow the rule:

* **`hunts.open` mixes churn rates.** Its read set is the hunt, its realms, every quiz row of the
  hunt, its expressions, *and every widget of every quiz* (`expressionUsageOf`, `convex/hunts.ts:33`).
  A widget change in any quiz reruns it; a reorder or lock of any quiz reruns it (quiz rows carry
  `row_ordering`, `locked`, `last_sortkey`, `bulk_ishes_last`). The usage count is only shown in
  the Expressions modal. Split it: `hunts.open` reads hunt, realms and the quiz listing;
  `expressions.forHunt` (with usage) is subscribed by the modal and the widgets editor only.
  Further, if the listing needs only labels and titles, a quiz's screen-state fields could move
  to a row of their own so the listing's read set stops churning with every sort.
* **`reviews.forQuiz` is on the smith's critical path.** `findingOf` in `use-hunt.ts` will not
  say "found" until the reviews have arrived, and the smith's screen shows only the shared ones.
  The review screen needs them; the workbench does not. Subscribe to reviews from the screen
  that shows them.

### 2b. What Convex offers, against urql's graphcache

Nothing like graphcache, and that is by design. Concretely, from the installed client
(`convex` 1.46, `convex-helpers` 0.1.124):

* **The cache is keyed by query function plus arguments**, not by entity
  (`browser/sync/local_state.js`: one `querySet` entry per serialized path and args, reference
  counted). Two queries returning the same document hold two copies. There is no normalization
  and no "hydrate this list from what the parent already fetched".
* **Identical subscriptions are deduplicated.** Two `useQuery(api.questions.open, { question_id })`
  calls, or a `useQuery` and a `watchQuery`, share one server subscription. This is why
  `useHistoryFeed`'s watches cost no extra network.
* **Invalidation is server-side, per query, by read set.** The client never guesses what a
  mutation changed; the server reruns every subscribed query whose read set was touched and
  pushes only the ones whose result differs. Consistency across queries is guaranteed (every
  push is one transaction's view), which graphcache cannot promise.
* **The server function is the normalization layer.** Joins are written once in the query
  (`lib/rows.ts` projections; `convex-helpers/server/relationships` has `getAll`,
  `getManyFrom`, `getManyVia` for the mechanics). Sparse lists hydrating transparently in the
  parent is not a thing; instead you write the query that returns what the screen needs.
* **Optimistic updates are per query, not per entity** (`useMutation(...).withOptimisticUpdate`):
  you patch the cached result of each affected query by its arguments. The opposite of
  graphcache's "update the entity and every list follows", and the reason to keep the number of
  query shapes small if optimistic updates ever arrive.
* **`useQueries`** for a dynamic set of subscriptions from one hook; **`usePaginatedQuery`** for
  unbounded lists; **`client.query`** for a one-shot read; **`Watch.localQueryResult`** to read
  the cache outside React.
* **`ConvexQueryCacheProvider`** (`convex-helpers/react/cache`) keeps a subscription alive for a
  TTL after its last hook unmounts, so navigating back is instant. It costs bandwidth, not saves
  it; worth it for the switcher (quiz to quiz within a realm) once on the cloud.

### 2c. Fetch wide, subscribe narrow

Convex has no primitive for "subscribe to a subset of a result". A subscription's cost is the
result's size times how often its read set changes, so the idiom is to subscribe to several
narrow queries whose union is the screen, and let dedupe and the server cache do the rest. That
is what is built.

Where a wide one-shot read earns its place is the first paint: the frame-then-questions shape
costs one extra round trip before a quiz shows, and adding a question costs one more before the
row appears (measured: 115 ms locally, 261 ms at an 80 ms network). If the cloud makes that
felt, the fix is small and local to `useQuiz`: a one-shot `client.query(quizzes.whole)` on
mount whose result stands in until every per-question subscription has delivered, overlaying by
question id. `useQuiz` already holds "the quiz last read whole" for the add-a-question case, so
the overlay is the same mechanism with a different seed. Do not subscribe to the wide query as
well: that reintroduces the rerun-everything cost the split removed.

## 3. Database residue in the models

The row validators are Convex-shaped and clean. The whiff is on the *tree* side, which still
assumes the browser builds and ships whole quizzes, as it did under Jazz:

* **Every model has two shapes**, `quiz` (tree) and `row`, and `chains_to` means an id in one and
  a label in the other, translated in `quizFromSeen` and `writeQuestions`. The tree exists for
  three reasons now: `Quiz.blank`/`Hunt.blank` (built on the server anyway, then diffed into
  rows by `writeQuiz` with `held: null`), the import merge (`importing.ts` works on a tree, then
  `replace_open_quiz` ships the whole tree to the server), and the export and git mirror. The
  first could build rows directly; the second could send a list of question patches plus adds;
  the third is a projection and needs no `_id` at all. If the tree stays, it is as a read-only
  projection, and `treeid`, `mintId` and the tree-level integrity checks go with the write path.
* **`treeid` accepts a Convex id, a UUID or a ULID** (`lib/validator.ts:53`), and `CK.ulid`,
  `PA.Ulid` and `mintId` exist so a tree can be built before it is written. The ULID arm is for
  exports from before September; CLAUDE.md says there is no data to preserve, so it can go
  unless the Coach's own backups need it. `import.ts:51` likewise still parses a `workspace`
  export with `active_quiz_id`, and `importing.ts` matches quizzes by a foreign `id` first.
* **Bot replies are stored twice in spirit.** Rows are append-only bottings; the tree carries
  `guess`/`clueing_ishes`/`hint_ishes` as Jazz-era cell objects with `updated_at`, `stale`,
  `last_err`. `resultsFor` derives the tree shape from rows; `unrecordedBottings` diffs it back
  by timestamp; and `recordResult` (`quiz_actions.ts:232`) builds a fake question named `alone`
  so it can reuse that diff for a single reply. The `set_guess`/`set_ishes` actions carry the
  client's `Date.now()` as `updated_at`, which the row then discards for `_creationTime`. A
  `record_reply` action taking `{ question_id, slot, reply }` and inserting one row would delete
  most of `models/botting.ts`'s second half and the `askError` shuffle.
* **Type surgery around ids**: `IdentT = row & { _id: string }` (`ident.ts:22`) and
  `BottingT = Omit<row, 'question_id'> & { question_id: string }` (`botting.ts:51`) widen Convex
  ids to strings so the tree can hold UUIDs. Goes with the point above.
* **Hunt and Quiz `.check(integrityIssues)`** duplicate, on the tree, what the mutations enforce
  in the transaction (label taken, chain dangling). Fine while the tree is written whole; another
  reason to stop doing that.
* **Nothing Turso-shaped remains.** No JSON-text columns, no Drizzle, no `created_at` on rows;
  the two `updated_at`s left are the cell objects above.

## 4. Hand-rolled and workaround code

Recorded and approved (listed for completeness, not re-opened): the bespoke `<table>` grid and
its sort-header `<button>` (`QuestionTable.tsx:102`); `useChecklist`; and drag-and-drop through
Pragmatic DnD with the arrow keys answered in `useReorderable`.

Not on the approved list:

* **A personal lodash under `src/lib/`.** `strings.ts` (404 lines: `toSentence` with an
  eight-shape `manyAndLast` union, `hardcapList`, `qt`/`dqt`/`qtc`/`comma`, `indent`/`dedent`),
  `collections.ts` (`arrNZ`, `cheatNZ`, `arrNZToFill`, `scrubNil`, `scrubVoid`, `clxnsize`,
  `appendMutatingly`), `props.ts` (`adorn`, `decorate`, `getProp` and six more descriptor
  helpers), `errors.ts` (fourteen error classes with factories), `type-tools.ts`. Outside their
  own files and tests, the only uses in `src/` are `Inconsistent` (twice) and the three
  functions `vv/reporting.ts` needs (`toSentence`, `smush`, `shortenWithEllipsis`). Everything
  else is unused. This is the largest single finding: `es-toolkit` is the sanctioned toolkit
  and this is its home-brew twin, carried over from the relics with their tests. Recommend
  deleting all but what `reporting.ts` and `refusals.ts` call, and inlining those.
* **Unused validator checks.** `vv/checks/contact.ts` (email, phone, postcode, PO box, given
  name...), `vv/checks/numbers.ts` (latitude, longitude, money, port numbers) and most of
  `vv/checks/strings.ts` and `vv/patterns.ts` are imported by nothing but their tests. Same
  origin. Keep the seven or so the models use (`textish`, `noteish`, `titleish`, `label`,
  `identlabel`, `formulaish`, `convexid`) and delete the rest.
* **Two kits.** `lib/vv/kit.ts` exports `Kit` and `lib/validator.ts` exports `ValidatorKit`,
  overlapping aliases with different names (`bag` there, `rec` here). Only `vv/checks/*` import
  `Kit`. One should go.
* **`inspectify-browser.ts`** is a 148-line reimplementation of `util.inspect` for the browser.
  Used by the error map to quote a refused value. A library owns this (`object-inspect`, a few
  kilobytes, no dependencies); or the browser could use `UU.jsonify` and lose a little fidelity
  on `undefined` and `Map`.
* **`Validator`'s callable wrapper** (`lib/validator.ts`: `callable`, `plain`, `unwrapped`) sets a
  Zod schema as the prototype of a function so `Foos.foo(dna)` parses, then mutates schema
  definitions in place to unwrap them for `toJSONSchema`. It saves `.parse` at every call site
  at the cost of prototype tricks that the JSON Schema exporter needs undoing. Clever in the way
  CLAUDE.md says to propose rather than do; I would propose keeping the namespacing and dropping
  the callability.
* **`use-settled-resize.ts:27`** attaches a native `resize` listener and debounces it with a
  hand-rolled timer. `_.debounce` from es-toolkit does the timer; a `ResizeObserver` on the
  scroller would be the DOM's own answer. Tripwire: a native handler beyond click/change.
* **`commit-scheduler.ts`** is a hand-rolled leading-edge throttle per quiz (fire after
  `seconds`, ignore later notes until then). `_.throttle` with `{ leading: false }` or a
  `debounce` with `maxWait` covers it; the per-quiz map is the only part that is ours.
* **`quiz-mirror.ts:19` `takeTurn`** is a hand-rolled async mutex (a promise chain as a queue).
  Small and correct; a library (`async-mutex`) exists but adding a dependency for eight lines is
  not obviously better. Flagging, not recommending a change.
* **`use-draft.ts`** is form state by hand (draft, commit on blur, external change wins when not
  editing). The tripwire names form state; at 47 lines and used by nine fields it is proportionate,
  and MUI has no controlled-draft primitive. Flagging once.
* **Raw elements where MUI has the component, outside the grid**: `<select>` in
  `QuizSwitcher.tsx:32` (chrome, not the grid) and `cells/chain.tsx:20`; `<input>` and `<button>`
  in `QuizHeader.tsx:24-36`; `<button>` in `cells/ErrBadge.tsx:25`; `<textarea>` in
  `panels/ImportPanel.tsx` and `panels/ReadonlyBox.tsx`. The cells arguably sit under the grid
  decision (the chain picker is on the hot path); the switcher, header and panels do not, and
  are the tripwire's "raw `<button>` where MUI has one".
* **`formulas.ts:98` timeboxing** hooks JSONata's `__evaluate_entry`/`__evaluate_exit`. These are
  the hooks JSONata's own exerciser uses for the same purpose, but they are not in its public
  API and are looked up by name inside the evaluator. Works on 1.8.9, which is pinned; note it
  beside the pin in `notes/stack.md`.
* **Two registries of in-flight writes.** `use-hunt.ts:95` keeps a module-level `Writing.count`
  for `beforeunload` while `useHunt` also keeps a `writing` state for `unsaved`, and
  `quiz-mirror.ts` keeps a `writing` set for `writesLanded`. Three views of the same fact.

## 5. Complexity

Most complicated, and fairly so:

* **`convex/writing/quiz_writing.ts`** (`writeQuiz`, `writeQuestions`, `writeWidgets`,
  `writeColumns`): a diff-write of a whole tree into rows. Earns its complexity while the import
  ships a whole tree (see section 3); would shrink to nothing if it did not.
* **`src/lib/importing.ts`** (296 lines): two-pass merge by label with foreign-id chain
  remapping and three accepted payload shapes. Inherent to "paste back anything Export ever gave
  you", but the workspace shape and id-first matching are compatibility with exports that no
  longer exist.
* **`src/components/QuestionRow.tsx`** and `cells/fields.tsx`: row-height negotiation through
  layout effects and a resize token. Inherent to the approved bespoke grid.

More complicated than their stated purpose implies:

* **`src/state/use-hunt.ts`** (254 lines). Its purpose is "the quiz the address names, live, and
  a dispatcher". It also: places an address in a hunt and follows a relabel (`placeIn`, with the
  set-state-during-render trick); feeds the git mirror through a second, watch-based assembly
  of the same quiz (`useHistoryFeed`, which re-implements `useQuiz`'s follow-the-order logic on
  `watchQuery` so the mirror hears a change before the mutation resolves); holds the page on
  `beforeunload`; and tracks writes for the mirror. Four concerns in one hook. The history feed
  in particular is a whole parallel subscription graph for one consumer; if the mirror could
  accept hearing a change one render later, it would collapse into an effect on `useQuiz`'s
  result.
* **The git mirror as a subsystem**: `quizgit.ts` (488), `quiz-mirror.ts` (253),
  `commit-scheduler.ts` (93), `changes.ts` (177), plus `exposure.ts` and half of `exporting.ts`
  serving it, about 1,100 lines plus 540 of tests, for "a past-versions view and an exit door".
  It carries its own filesystem abstraction, mutex, flush-on-pagehide, milestone and mark tags
  with collision suffixes, a repository lister, and a shorthand commit-message language.
  `quiz-mirror.ts` has module-level side effects (the scheduler is built and document listeners
  attached at import) and no unit test. The Coach's open question about lightning-fs versus
  OPFS is the moment to ask whether the mirror needs all of this, or whether "commit the
  `.tq.json` and `.qq.tsv` on a timer, tag on request" is the whole feature.
* **`src/models/botting.ts`** (243 lines): the tree-to-rows-and-back machinery described in
  section 3. Half of it disappears with a `record_reply` action.
* **`src/lib/validator.ts`** (201 lines) for what is, at heart, `Object.fromEntries` over a bag of
  schemas: the callable wrapper and its unwrapping are two thirds of the file.
* **`src/lib/strings.ts`** (404 lines) and **`src/lib/vv/reporting.ts`** (268 lines): a sentence
  joiner with eight cases, and a Zod error map with digit grouping and four words for nothing.
  The error map is used and its messages are good; the joiner exists to serve it and could be
  ten lines.
* **`hunts.open`**, as a query: see 2a. Its read set is the whole hunt's widgets for one count.

## 6. Suggested order

1. Delete the unused utility library and unused checks; collapse the two kits. Pure removal,
   large, low risk.
2. Fix the per-keystroke retitle; subscribe to reviews from the review screen; split expression
   usage out of `hunts.open`. Three small changes, each measurable with the phase 4 harness.
3. Replace the "never a query per row" lines in the plan, the decision and `notes/stack.md`
   with the rule in 2a, and record `qq` in STYLE.md.
4. Decide the tree's future (section 3): a `record_reply` action first, since it deletes the
   most; then whether import sends patches rather than a tree.
5. Sweep the style items in section 1 (lambda indexes, doc-block notes, id naming, `Sync*`).
